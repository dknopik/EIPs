## Abstract

[EIP-7732](./eip-7732.md) propagates the execution payload as a single message on the `execution_payload` gossipsub topic. This EIP replaces it with a Waggle topic of the same name. Waggle is a libp2p publish-subscribe protocol for objects that peers reconstruct from pieces. The payload envelope is split into `TOTAL_EXECUTION_PAYLOAD_CHUNKS` chunks, which peers push to each other, announce and request until each of them holds every chunk. The builder commits to the chunk set with a Merkle root carried in the execution bid, so each chunk is independently verifiable with an inclusion proof against the bid of the beacon block it belongs to.

## Motivation

The gas-limit growth that [EIP-7732](./eip-7732.md) enables implies larger payloads leading to increased latency. If Payload Timeliness Committee (PTC) members do not receive the payload within the attestation deadline, an otherwise valid payload is considered missed.

The existing `execution_payload` gossipsub topic scales poorly as payloads grow. Two effects dominate:

1. Once a peer has received a large message, it is hard to cancel in-flight duplicates, so the same bytes arrive several times and consume bandwidth that could carry new data.
2. A peer must download the full message before it can forward any of it, so each hop adds a full transfer, leading to increased latency proportional to message size multiplied by hop count.

Both effects are mitigated when the message is chunked. Large duplicates are impossible with chunk granularity, and a peer can forward each chunk as soon as it arrives, so hops overlap instead of serializing.

Gossipsub, however, routes each chunk as an independent message. A peer can tell its mesh peers about the chunks it holds only one message at a time, through control messages such as `IDONTWANT` and `IHAVE`, and recovers a missing chunk through heartbeat-driven `IHAVE`/`IWANT` gossip. Waggle makes the payload the unit of dissemination instead: peers exchange bitmaps of the chunks they hold, push new chunks to peers that lack them, and request missing chunks directly.

### Commitment

The execution bid commits to the chunked envelope:

```python
class ExecutionPayloadBid(ProgressiveContainer):
    ...
    payload_chunks_root: Root  # [New in this EIP]
    ...
```

`payload_chunks_root` is the SSZ `hash_tree_root` of the `Vector[Bytes32, TOTAL_EXECUTION_PAYLOAD_CHUNKS]` of SHA-256 hashes of the chunks of the serialized `ExecutionPayloadEnvelope`, as computed by `compute_payload_chunks_root` in the Chunking section. A receiver therefore verifies one bid signature and, per chunk, one Merkle inclusion proof. Once the envelope is reconstructed, it is verified as described in the Envelope verification section.

### Envelope

Chunking is applied to the envelope:

```python
class ExecutionPayloadEnvelope(ProgressiveContainer):
    payload: ExecutionPayload
    execution_requests: ExecutionRequests
    builder_index: BuilderIndex
    # [Modified in this EIP] removed `beacon_block_root`
    parent_beacon_block_root: Root
```

`beacon_block_root` is removed because it is not known at the time of envelope construction.

Under [EIP-7732](./eip-7732.md) the builder constructs the envelope after observing that its bid was included, and can therefore embed the beacon block root. Under this EIP the builder must commit to the chunks when it produces the bid — before the block exists — so the root cannot be part of the committed bytes. Instead, the beacon block root identifies the payload on the network: it is the Waggle object ID under which the chunks are disseminated, and receivers verify the chunks against the `payload_chunks_root` of the bid in the block with that root. Where [EIP-7732](./eip-7732.md) reads the root from the envelope, it is passed alongside the envelope instead.

`SignedExecutionPayloadEnvelope` is removed, and the builder does not sign the envelope: the signature on the bid authenticates it through `payload_chunks_root`.

### Chunking

The builder MUST derive the chunks, and therefore `payload_chunks_root`, as follows. No padding is added: the last non-empty chunk can be shorter, and trailing chunks can be empty.

```python
def compute_payload_chunks(
    envelope: ExecutionPayloadEnvelope,
) -> Vector[Chunk, TOTAL_EXECUTION_PAYLOAD_CHUNKS]:
    data = serialize(envelope)
    chunk_size = (len(data) + TOTAL_EXECUTION_PAYLOAD_CHUNKS - 1) // TOTAL_EXECUTION_PAYLOAD_CHUNKS
    chunks = []
    for i in range(TOTAL_EXECUTION_PAYLOAD_CHUNKS):
        start = i * chunk_size
        chunks.append(Chunk(data[start:start + chunk_size]))
    return chunks


def compute_payload_chunks_root(envelope: ExecutionPayloadEnvelope) -> Root:
    leaves = Vector[Bytes32, TOTAL_EXECUTION_PAYLOAD_CHUNKS](
        [hash(chunk) for chunk in compute_payload_chunks(envelope)]
    )
    return hash_tree_root(leaves)
```

Each chunk is disseminated in a `PayloadChunk`, along with its index and its inclusion proof:

```python
class PayloadChunk():
    index: ChunkIndex
    chunk: Chunk
    chunk_inclusion_proof: Vector[Bytes32, CHUNK_INCLUSION_PROOF_DEPTH]
```

Each leaf is `hash(chunk)`, the SHA-256 hash of the chunk's bytes; `chunk_inclusion_proof` is the corresponding Merkle branch:

```python
def verify_payload_chunk_inclusion_proof(
    payload_chunk: PayloadChunk,
    payload_chunks_root: Root,
) -> bool:
    return is_valid_merkle_branch(
        leaf=hash(payload_chunk.chunk),
        branch=payload_chunk.chunk_inclusion_proof,
        depth=CHUNK_INCLUSION_PROOF_DEPTH,
        index=payload_chunk.index,
        root=payload_chunks_root,
    )
```

Receivers concatenate chunks `0` through `TOTAL_EXECUTION_PAYLOAD_CHUNKS - 1` and deserialize the result; nothing is stripped, since each leaf hashes its chunk's exact bytes.

### Envelope verification

The envelope is verified against the commitment in the bid instead of a signature, and the beacon block root is passed alongside it:

```python
def verify_execution_payload_envelope(
    state: BeaconState,
    # [Modified in this EIP] The envelope is not signed
    envelope: ExecutionPayloadEnvelope,
    execution_engine: ExecutionEngine,
) -> None:
    payload = envelope.payload
    bid = state.latest_execution_payload_bid

    # [Modified in this EIP]
    # Verify the commitment instead of the signature and the beacon block root
    assert compute_payload_chunks_root(envelope) == bid.payload_chunks_root

    # [Unchanged from EIP-7732] The remaining checks, from the
    # `parent_beacon_block_root` check onwards
    ...


def on_execution_payload_envelope(
    store: Store,
    # [New in this EIP]
    beacon_block_root: Root,
    # [Modified in this EIP] The envelope is not signed
    envelope: ExecutionPayloadEnvelope,
) -> None:
    # The corresponding beacon block root needs to be known
    assert beacon_block_root in store.block_states

    # Check if blob data is available
    # If not, this payload MAY be queued and subsequently considered when blob data becomes available
    assert is_data_available(beacon_block_root)

    state = store.block_states[beacon_block_root]

    # Verify the execution payload envelope
    verify_execution_payload_envelope(state, envelope, EXECUTION_ENGINE)

    # Add execution payload envelope to the store
    store.payloads[beacon_block_root] = envelope
```

`state` is the post-state of the beacon block, whose bid signature was verified when the block was processed, so the commitment check both authenticates the envelope and binds it to the block. As it recomputes the root from the envelope, it also rejects envelopes that the builder did not split as specified in the Chunking section, and covers envelopes obtained other than through chunks, which carry no inclusion proofs. A node that reconstructed the envelope from valid chunks MAY instead check that each chunk has the length that `compute_payload_chunks` gives it.

### Networking

This EIP deprecates the `execution_payload` gossipsub topic. Execution payloads are instead disseminated over Waggle, on the Waggle topic `execution_payload`.

#### Waggle

Waggle is the libp2p publish-subscribe protocol for objects that peers reconstruct incrementally from pieces, with the protocol ID `/waggle/1.0`. Nodes MUST implement it as specified by libp2p, and this EIP assumes familiarity with that specification. Each Waggle message is about one object, and carries its `objectID` and, optionally, `piecesMetadata` and `pieces`. Waggle leaves the meaning of these fields to the application, and neither validates nor forwards messages itself. The following sections define them for execution payloads, along with how nodes validate and disseminate them.

#### Topic

The topic ID is the UTF-8 encoding of `/eth2/{fork_digest}/execution_payload/ssz_snappy`, with `fork_digest` formatted as in gossipsub topic names. Like the data of gossipsub messages, chunks are SSZ serialized and then compressed with Snappy block compression, hence the `ssz_snappy` encoding. Like gossipsub control messages, chunk metadata is not compressed, as it is too small to benefit. Nodes subscribe to and unsubscribe from the topic of each fork digest as they do for gossipsub topics around fork transitions.

The payload of a beacon block is disseminated on the topic of the fork digest of the block's epoch.

#### Messages

Each message on the topic is about the execution payload of one beacon block, and carries the following:

| Waggle field | Content |
| --- | --- |
| `objectID` | The `hash_tree_root` of the `BeaconBlock` whose bid commits to the payload |
| `piecesMetadata` | If present, a `ChunkMetadata`, SSZ serialized |
| `pieces` | If present, a single `PayloadChunk`, SSZ serialized and Snappy compressed |

```python
class ChunkMetadata():
    slot: Slot
    have: Bitvector[TOTAL_EXECUTION_PAYLOAD_CHUNKS]
    request: Bitvector[TOTAL_EXECUTION_PAYLOAD_CHUNKS]
```

`slot` is the slot of the beacon block. `have` marks the chunks the sender holds, all of which it validated, and `request` the chunks the sender asks the receiver to send.

Each chunk is compressed on its own, and the commitment covers the uncompressed chunks. Let `max_chunk_length` be the length of the largest valid `PayloadChunk`, whose chunk is `MAX_PAYLOAD_CHUNK_SIZE` bytes long, and `max_compressed_len` the worst-case length of Snappy compression, as defined for gossipsub. Nodes MUST NOT send messages on the topic that exceed the following limits, and MUST treat messages that exceed them as malformed:

- The encoded Waggle message, including its framing, is at most `max_compressed_len(max_chunk_length) + 1024` bytes long, which leaves room for `objectID`, `piecesMetadata` and the framing. Nodes MUST set the maximum message size of Waggle for the topic to this limit.
- The uncompressed length in the Snappy header of `pieces` is at most `max_chunk_length`. Nodes MUST check it before decompressing `pieces`.
- `pieces` is at most `max_compressed_len(n)` bytes long, where `n` is the uncompressed length in its Snappy header.

#### Payload state

A node MUST track the payload of each beacon block that passes the `beacon_block` gossip validation, which admits only the first block with a valid signature for each slot and proposer, and only from the proposer that the shuffling expects for the slot. It SHOULD track the payload of each other valid beacon block, for example one it obtained through a lookup. In either case, it does so only for blocks of the current slot, within `MAXIMUM_GOSSIP_CLOCK_DISPARITY` allowance, from the moment it validates the block until `MAXIMUM_GOSSIP_CLOCK_DISPARITY` after the end of the block's slot, and MAY discard its state afterwards. The payload's chunks are verified against `block.body.signed_execution_payload_bid.message.payload_chunks_root`. For each payload, a node keeps the valid chunks it holds and, per peer, the chunks the peer is known to hold: those it announced in `have`, sent to the node, or received from the node.

Once the builder observes a beacon block containing its bid, it tracks the payload of the block with all chunks valid, and disseminates them as described below. Other nodes SHOULD send their `ChunkMetadata` to their peers on the topic when they start tracking a payload, so that the peers tell them which chunks they hold.

Once a node holds every chunk of a payload, it reconstructs the envelope as described in the Chunking section. It then checks the envelope as the `execution_payload` gossip validation of [EIP-7732](./eip-7732.md) did, with the root of the block in place of `envelope.beacon_block_root`, except for the signature and duplicate envelope checks. If the envelope deserializes and passes these checks, the node records `seen.execution_payloads[payload.block_hash] = payload`, as that validation did, and calls `on_execution_payload_envelope` with the root of the block and the envelope. Otherwise the payload is invalid. As its chunks are valid, this is the builder's fault, and the node does not penalize its peers. `seen.execution_payload_envelopes`, which only that validation used, is removed.

A member of the Payload Timeliness Committee sets `payload_present` according to when the envelope passed these checks, rather than when it saw a `SignedExecutionPayloadEnvelope` referencing the block.

#### Validation

There is no gossipsub validation on Waggle topics. Instead, a node checks each message it receives as follows. _[IGNORE]_ means the node drops the message. _[REJECT]_ means the node drops the message and SHOULD penalize the sender. Nothing from a dropped message is used or forwarded.

- _[REJECT]_ The message is well-formed: it is within the size limits above, `objectID` is 32 bytes long, `piecesMetadata`, if present, deserializes, and `pieces`, if present, decompresses and deserializes.
- _[IGNORE]_ The node tracks the payload of the block with root `objectID`. Peers often learn about a payload before a node has validated its block, and do not send the node a chunk again, so a node SHOULD buffer messages about payloads it does not track yet, if the message or an earlier message of the same sender about the same object carries a `slot` equal to the current slot (within `MAXIMUM_GOSSIP_CLOCK_DISPARITY` allowance), and check them once it tracks the payload. Buffering MUST be bounded, in total and per peer. If the block remains unknown for a while, the node SHOULD look it up by root from the senders, and MAY slightly penalize the senders of messages about payloads it never learns about.
- _[IGNORE]_ The message arrived on the topic of the fork digest of the block's epoch.

For a message about the payload of a tracked beacon block `block`, carrying the `PayloadChunk` `chunk`:

- _[REJECT]_ `chunk.index` is less than `TOTAL_EXECUTION_PAYLOAD_CHUNKS`.
- _[REJECT]_ The sender has not sent the node a chunk with index `chunk.index` of this payload before.
- _[REJECT]_ The inclusion proof is valid as verified by `verify_payload_chunk_inclusion_proof(chunk, block.body.signed_execution_payload_bid.message.payload_chunks_root)`. A node that already holds the chunk at `chunk.index` MAY compare the chunks instead.

For a message about the payload of a tracked beacon block `block`, carrying the `ChunkMetadata` `metadata`:

- _[REJECT]_ `metadata.slot` equals `block.slot`.
- _[REJECT]_ `metadata.have` includes every chunk the sender announced in earlier `ChunkMetadata` about this payload.
- _[REJECT]_ `metadata.request` includes none of the chunks the sender announced in `have`, or sent to the node.

#### Dissemination

The following parameters tune the dissemination. They are not part of consensus, and nodes MAY use different values, except that `PUSH_PEERS` is a minimum, which nodes MAY exceed.

| Name | Recommended value | Description |
| --- | --- | --- |
| `PUSH_PEERS` | `10` | Minimum number of peers each newly valid chunk is pushed to |
| `MAX_REQUESTS_PER_PEER` | `4` | Maximum number of chunks requested from a peer at a time |
| `REQUEST_DELAY` | `500` milliseconds | Time after a node starts tracking a payload before it requests missing chunks |
| `REQUEST_TIMEOUT` | `500` milliseconds | Time after which a requested chunk can be requested again |

A node disseminates the chunks of the payloads it tracks to its peers on the topic:

- **Push.** When a chunk becomes valid, the node MUST send it right away to at least `PUSH_PEERS` peers not known to hold it, or to every such peer if there are fewer, and MAY send it to more. It SHOULD prefer the peers with the fewest pending messages, so that a publisher spreads distinct chunks across its peers.
- **Announce.** The node MUST send its `ChunkMetadata` to each peer whenever its `have` changed since it last told that peer, and MAY coalesce the announcements of chunks that become valid in a burst. The first message a node sends a peer about a payload SHOULD carry its `ChunkMetadata`, so that a peer that does not track the payload yet learns its slot, and can buffer the message. When a peer sends its first `ChunkMetadata` about a payload, the node SHOULD send its own again, as the peer may have dropped earlier messages.
- **Request.** The node SHOULD request the chunks it lacks from peers that announced them, through `request`, with at most `MAX_REQUESTS_PER_PEER` requests outstanding per peer. A chunk not received within `REQUEST_TIMEOUT` SHOULD be requested again, possibly from another peer. A node SHOULD NOT send requests within `REQUEST_DELAY` after it starts tracking the payload.
- **Serve.** The node MUST send requested chunks it holds right away, unless it pushed them to the requester before.

To avoid being penalized, a node MUST NOT send a peer a chunk it sent the peer before, MUST NOT request a chunk from a peer it announced or sent that chunk to, and MUST NOT remove a chunk from `have` once announced.

#### Request/response

`ExecutionPayloadEnvelopesByRange` and `ExecutionPayloadEnvelopesByRoot` gain a version 2 for the envelopes of this EIP, with the protocol IDs `/eth2/beacon_chain/req/execution_payload_envelopes_by_range/2/` and `/eth2/beacon_chain/req/execution_payload_envelopes_by_root/2/`. Each response chunk carries an envelope along with the root of its beacon block:

```python
class ExecutionPayloadEnvelopeWithRoot():
    beacon_block_root: Root
    envelope: ExecutionPayloadEnvelope
```

Otherwise, version 2 is identical to version 1, with `beacon_block_root` in place of `signed_execution_payload_envelope.message.beacon_block_root`: `ExecutionPayloadEnvelopesByRoot` requests envelopes by it, and it determines the fork digest context of each response chunk. A node passes a received envelope to `on_execution_payload_envelope` along with its `beacon_block_root`, whose commitment check rejects an envelope paired with the root of a block whose bid does not commit to it.

Version 2 only serves the envelopes of the fork that activates this EIP and later forks, as it carries no signatures. Version 1 remains for the envelopes of earlier forks, which are authenticated by their signatures, and only serves those. A node requests envelopes with the version that serves the fork of the requested slots or blocks, and responds only with the envelopes that the version of the request serves.

### Open questions and future considerations

- The networking scheme could be extended by erasure coding the chunks, so that a receiver can reconstruct the envelope from a subset of chunks. This introduces additional complexity and may lead to higher bandwidth usage. However, it may mitigate "coupon collector" problems, where a receiver missing a small number of chunks may wait a long time to receive them. Waggle does not require pieces to be slices of the object, so it can carry erasure-coded chunks as well.
- In future it might be considered to introduce a `bal_chunks` topic following the same broadcasting scheme for Block Access List (BAL, [EIP-7928](./eip-7928.md)) messages, which are currently part of the execution payload. This would allow BAL message propagation to start sooner than the rest of the payload.

## Rationale

**Why a Merkle commitment.** Alternatives such as KZG place proof generation on the builder's critical path. A Merkle tree over chunks is cheap enough to build at bid time, and a single root in the bid makes each chunk self-verifying against one already-verified signature.

**Why `TOTAL_EXECUTION_PAYLOAD_CHUNKS = 64`.** The value is not derived from measurement; smaller chunk counts already show benefit compared to single large messages. 64 is chosen for forward compatibility in case we decide to extend protocol erasure coding via `c-kzg`, which segments data into 64 chunks and extends them to 128.

**Why unpadded `ByteList` chunks.** SSZ has no outer length prefix, so padding bytes would deserialize as envelope data; hashing each chunk's exact bytes commits its true length instead. Pinning the split and merkleization to SSZ lets two clients derive identical roots with existing code.

**Why Waggle.** Gossipsub disseminates complete messages and has no notion of a payload made of chunks. With Waggle, peers exchange the set of chunks they hold per payload, so a node pushes a chunk only to peers not known to hold it, and fetches the chunks it lacks with requests instead of waiting for them to be pushed or gossiped. All chunks of a payload share one object ID, so each chunk carries only its index and inclusion proof, rather than the commitment, slot and block root. Each Waggle topic uses its own streams, so payload chunks do not queue behind messages on gossipsub topics, nor delay them. Waggle also leaves peer scoring to the application, so penalties follow the validity rules of this EIP.

## Backwards Compatibility

The `execution_payload` gossipsub topic is removed, and nodes must support Waggle, so this change is not backwards compatible and requires a fork.

## Security Considerations

Chunks are not individually signed; their authenticity derives entirely from the bid signature via `payload_chunks_root`. A node verifies chunks only against the commitment in the bid of a beacon block it has validated, and only forwards valid chunks, so unsigned chunk spam is filtered at the first hop.

The `slot` in `ChunkMetadata` is covered by neither the bid signature nor the inclusion proof. Once the block is known, a divergent `slot` is rejected. Before that, `slot` only decides whether a message is buffered, so a peer can make a node buffer messages about made-up payloads of the current slot, and look up their blocks. The bounds on buffering, in total and per peer, limit the memory this takes, and the senders can be penalized once the slot passes without the block becoming known.

Per-index equivocation is not possible: two distinct chunks that both verify at the same index against the same `payload_chunks_root` would imply a collision in the Merkle tree, so at most one chunk per index can propagate for a given payload.

The `chunk.index` bound is load-bearing: `is_valid_merkle_branch` reads only the low `CHUNK_INCLUSION_PROOF_DEPTH` bits, so an unbounded index would let the same chunk propagate again at `index + k * TOTAL_EXECUTION_PAYLOAD_CHUNKS`.

Requests are part of the piece metadata, which Waggle does not interpret, so Waggle cannot bound them. A node serves each chunk of a payload at most once per peer, and rejects requests for chunks the peer announced or sent, so a peer can make it upload at most one copy of each payload in response to requests.

A node rejects messages larger than the largest valid message before parsing them and, as a Snappy header states the uncompressed length, chunks that would decompress beyond the largest valid chunk before decompressing them, so a peer cannot make it allocate more than that.

Validity of the chunks does not imply validity of the reconstructed envelope, which is still fully validated after reconstruction, by `verify_execution_payload_envelope` as modified in the Envelope verification section.
