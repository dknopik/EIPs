## Abstract

[EIP-7732](./eip-7732.md) propagates the execution payload as a single message on the `execution_payload` gossipsub topic. This EIP replaces it with a Waggle topic of the same name. Waggle is a libp2p publish-subscribe protocol for objects that peers reconstruct from pieces. The payload envelope is split into `TOTAL_EXECUTION_PAYLOAD_CHUNKS` chunks, which peers push to each other, announce and request until each of them holds every chunk. The builder commits to the chunk set with a Merkle root carried in the execution bid, so each chunk is independently verifiable with an inclusion proof against the bid of the beacon block it belongs to.

## Motivation

The gas-limit growth that [EIP-7732](./eip-7732.md) enables implies larger payloads leading to increased latency. If Payload Timeliness Committee (PTC) members do not receive the payload within the attestation deadline, an otherwise valid payload is considered missed.

The existing `execution_payload` gossipsub topic scales poorly as payloads grow. Two effects dominate:

1. Once a peer has received a large message, it is hard to cancel in-flight duplicates, so the same bytes arrive several times and consume bandwidth that could carry new data.
2. A peer must download the full message before it can forward any of it, so each hop adds a full transfer, leading to increased latency proportional to message size multiplied by hop count.

Both effects are mitigated when the message is chunked. Large duplicates are impossible with chunk granularity, and a peer can forward each chunk as soon as it arrives, so hops overlap instead of serializing.

### Parameters

| Constant | Value |
| --- | --- |
| `TOTAL_EXECUTION_PAYLOAD_CHUNKS` | `64` |

### Commitment

The execution bid commits to the chunks of the payload envelope:

```python
class ExecutionPayloadBid(ProgressiveContainer):
    ...
    payload_chunks_root: Root  # [New in this EIP]
    ...
```

The builder splits the SSZ serialization of the `ExecutionPayloadEnvelope` into `TOTAL_EXECUTION_PAYLOAD_CHUNKS` contiguous chunks of `ceil(n / TOTAL_EXECUTION_PAYLOAD_CHUNKS)` bytes, where `n` is the length of the serialization. No padding is added: the last non-empty chunk can be shorter, and trailing chunks can be empty. `payload_chunks_root` is the SSZ `hash_tree_root` of the `Vector[Bytes32, TOTAL_EXECUTION_PAYLOAD_CHUNKS]` of the SHA-256 hashes of the chunks, so each chunk can be verified on its own with a Merkle inclusion proof against the bid.

### Envelope

`beacon_block_root` is removed from `ExecutionPayloadEnvelope`, and `SignedExecutionPayloadEnvelope` is removed: the builder does not sign the envelope, as its signed bid commits to it.

Where [EIP-7732](./eip-7732.md) reads the root of the beacon block from the envelope, the root is passed alongside the envelope instead, for example to `on_execution_payload_envelope`. The envelope is verified by recomputing `payload_chunks_root` from it and comparing the result with the `payload_chunks_root` in the bid of the beacon block, in place of the checks of the envelope signature and `beacon_block_root`.

### Networking

The `execution_payload` gossipsub topic is replaced by a Waggle topic of the same name. Waggle is a libp2p publish-subscribe protocol for objects that peers reconstruct from pieces. Each Waggle message is about one object, and carries its `objectID` and, optionally, `piecesMetadata` and `pieces`. Waggle leaves the meaning of these fields to the application, as well as the validation of messages, the scoring of peers, and the dissemination strategy: which pieces and metadata to send to which peers, and when.

Each message on the topic is about the payload of one beacon block:

| Waggle field | Content |
| --- | --- |
| `objectID` | The root of the beacon block whose bid commits to the payload |
| `piecesMetadata` | Which chunks the sender holds, and which it requests from the receiver |
| `pieces` | A chunk, along with its index and inclusion proof |

Nodes disseminate payloads as follows:

- A node tracks the payload of each beacon block of the current slot that it validates. It verifies each chunk it receives against the `payload_chunks_root` in the bid of the block, and neither uses nor forwards chunks that fail verification.
- Where [EIP-7732](./eip-7732.md) has the builder broadcast its envelope, the builder instead publishes the chunks of the envelope on the topic.
- A node pushes each chunk it validates to some of its peers that are not known to hold it, and announces the chunks it holds to its peers.
- A node requests the chunks it lacks from peers that announced them.
- As peers can learn about a payload before a node validates its beacon block, a node buffers messages about payloads it does not track yet, within bounds.
- Once a node holds every chunk, it reconstructs the envelope, and validates and imports it as it would an envelope received on the `execution_payload` gossipsub topic.
- A member of the Payload Timeliness Committee sets `payload_present` according to when it reconstructed and validated the envelope, rather than when it saw a `SignedExecutionPayloadEnvelope`.

`ExecutionPayloadEnvelopesByRange` and `ExecutionPayloadEnvelopesByRoot` gain a version 2, which serves the unsigned envelopes of this EIP, each along with the root of its beacon block.

### Open questions and future considerations

- The networking scheme could be extended by erasure coding the chunks, so that a receiver can reconstruct the envelope from a subset of chunks. This introduces additional complexity and may lead to higher bandwidth usage. However, it may mitigate "coupon collector" problems, where a receiver missing a small number of chunks may wait a long time to receive them. Waggle does not require pieces to be slices of the object, so it can carry erasure-coded chunks as well.
- In future it might be considered to introduce a `bal_chunks` topic following the same broadcasting scheme for Block Access List (BAL, [EIP-7928](./eip-7928.md)) messages, which are currently part of the execution payload. This would allow BAL message propagation to start sooner than the rest of the payload.

## Rationale

**Why a Merkle commitment.** Alternatives such as KZG place proof generation on the builder's critical path. A Merkle tree over chunks is cheap enough to build at bid time, and a single root in the bid makes each chunk self-verifying against one already-verified signature.

**Why `TOTAL_EXECUTION_PAYLOAD_CHUNKS = 64`.** The value is not derived from measurement; smaller chunk counts already show benefit compared to single large messages. 64 is chosen for forward compatibility in case we decide to extend protocol erasure coding via `c-kzg`, which segments data into 64 chunks and extends them to 128.

**Why unpadded chunks.** SSZ has no outer length prefix, so padding bytes would deserialize as envelope data; hashing each chunk's exact bytes commits its true length instead. Pinning the split and merkleization to SSZ lets two clients derive identical roots with existing code.

**Why the envelope does not contain the beacon block root.** Under [EIP-7732](./eip-7732.md) the builder constructs the envelope after observing that its bid was included, and can therefore embed the beacon block root. Under this EIP the builder commits to the chunks when it produces the bid, before the block exists, so the root cannot be part of the committed bytes. Instead, the root identifies the payload on the network as its Waggle object ID.

**Why Waggle.** Gossipsub disseminates every message in the same way. A node pushes each new message to all of its mesh peers for the topic, about `D = 8` of them, and at each heartbeat gossips the IDs of recent messages to a few other peers, which can then pull the messages they missed. The application validates messages and tunes parameters, but does not decide which peers receive what, or when. Gossipsub's Partial Message Extension, which the consensus specifications use for the cells of data columns, lets the application choose which parts of a message to exchange, but only with the peers that gossipsub selects for the topic, and it still scores peers through gossipsub. Waggle instead leaves the dissemination strategy to the application, so the consensus specifications can tailor it to execution payloads:

- A payload is a single object of `TOTAL_EXECUTION_PAYLOAD_CHUNKS` chunks. As peers announce which of its chunks they hold, a node pushes each chunk only to peers not known to hold it, and requests the chunks it lacks from peers that announced them. Over gossipsub, each chunk would be an unrelated message, which a node pushes to all of its mesh peers unless they sent `IDONTWANT` for it in time.
- The builder is the only initial source of the payload, so its upload bandwidth bounds how fast the payload enters the network. It can send each chunk to only a few peers, and different chunks to different peers, so that every chunk is in the network as soon as possible and peers complete each other's payloads. A gossipsub publisher sends every message to at least all of its mesh peers, so the last chunk would leave the builder only after it uploaded the payload several times.
- A payload is due within its slot. A node can request the chunks it lacks when it needs them, rather than waiting until a peer that holds them gossips their IDs to it at a heartbeat, which gossipsub runs every 0.7 seconds on the beacon chain.
- Peers are chosen per chunk. A node can push to and request from any of its peers on the topic, for example preferring fast or idle peers, rather than only the members of a mesh that gossipsub maintains for all messages of the topic.

As the consensus specifications define the strategy, it can also be refined as experience is gained, for example to request the chunks that are rarest among a node's peers first, without changing Waggle. Beyond the strategy, all chunks of a payload share one object ID, so each chunk carries only its index and inclusion proof, rather than identifying its payload itself. Each Waggle topic uses its own streams, so payload chunks do not queue behind messages on gossipsub topics, nor delay them. And as Waggle leaves peer scoring to the application, penalties follow the validity rules of payload chunks rather than gossipsub's generic score function.

## Backwards Compatibility

The `execution_payload` gossipsub topic is removed, and nodes must support Waggle, so this change is not backwards compatible and requires a fork.

## Security Considerations

Chunks are not signed individually. A node verifies each chunk with its inclusion proof against the `payload_chunks_root` in the bid of a beacon block it has validated, and neither uses nor forwards chunks that fail verification, so peers cannot inject chunks that the bid does not commit to. Two distinct chunks that verify at the same index would imply a collision in the Merkle tree, so at most one chunk per index can propagate for a payload.

Valid chunks do not imply a valid envelope. The reconstructed envelope is fully validated before it is imported, as under [EIP-7732](./eip-7732.md), with the commitment check in place of the signature check.

As the envelope does not contain the root of its beacon block, it is bound to the bid rather than to the block. If a proposer equivocates with several blocks that include the same bid, the builder cannot reveal its payload for only one of them. At most one of these blocks can become canonical, so the payload is neither included nor paid for twice.

Waggle leaves the validation of messages to the application, and piece metadata is not authenticated. Nodes therefore bound the resources a peer can make them spend: they check the size of messages before parsing or decompressing them, buffer only a bounded number of messages about payloads whose beacon block they have not validated yet, and send each chunk of a payload to each peer at most once.
